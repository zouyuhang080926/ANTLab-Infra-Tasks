# 指标口径

冻结日期：2026-10-09

本文件定义本项目各项性能指标的含义、计算方法和测量位置。
**报告中的任何数字都必须能对应到这里的某一条定义。**

---

## 一、为什么必须先定口径

"响应 2 秒"这句话没有信息量：

- 是从发出请求算，还是从服务端收到算？
- 第一个字出现的 2 秒，还是全部写完的 2 秒？
- 算不算排队时间？算不算网络传输？

**口径不同，同一个系统能测出完全不同的结论。** 所以先定义清楚，再开始测。

## 二、请求时间轴

一次流式请求在时间上分成这几段：

```
客户端发出请求
   │
   ├─ ① 网络往返 + 服务端排队
   │
   ├─ ② 预填充 prefill（读完整个输入，建立内部状态）
   │
   ├─ ③ 首字产出 ← TTFT 到这里为止
   │
   ├─ ④ 逐字解码 decode
   │
   └─ ⑤ 最后一个字 + 传输结束 ← 总耗时到这里为止
```

② 是"读题"，④ 是"答题"。请求越长，② 越重；回答越长，④ 越重。

## 三、指标定义

### 3.1 客户端指标（本程序测量）

| 指标 | 定义 | 计算方式 | 测量位置 |
| --- | --- | --- | --- |
| **TTFT**（首字延迟） | 从发起请求，到收到**第一个非空内容分片** | `首个内容分片的到达时刻 − 请求发出时刻` | 客户端，流式 |
| **总耗时** | 从发起请求到收到结束标记 `[DONE]` | `收到 DONE 的时刻 − 请求发出时刻` | 客户端，流式 |
| **TPOT**（每字耗时） | 首字之后的平均出字间隔 | `(总耗时 − TTFT) ÷ (输出token数 − 1)` | 客户端计算 |
| **输出吞吐** | 单位时间产出的 token 数 | `输出token数 ÷ 总耗时` | 客户端计算 |

**必须说明的三点**：

1. **TTFT 包含网络往返与排队。** 客户端能观察到的最完整等待时间，与用户体感一致；
2. **只认非空内容。** 收到 HTTP 响应头、或者只含 `role` 的空分片都不算——那不是"用户看到的第一个字"；
3. **输出 token 数以服务端 `usage` 为准**，不按字符数估算（中文一个字可能对应多个 token）。

### 3.2 服务端指标（服务端自报，用于交叉校验）

来自返回体里的 `timings` 字段：

| 字段 | 含义 |
| --- | --- |
| `prompt_n` / `prompt_ms` | 本次实际处理的输入 token 数 / 耗时（prefill） |
| `predicted_n` / `predicted_ms` | 生成的 token 数 / 耗时（decode） |
| `cache_n` | 命中前缀缓存、**未参与计算**的 token 数 |

**客户端与服务端对不上的排查方向**：

- 客户端 TTFT 远大于服务端 `prompt_ms` → 差额是网络与排队；
- `prompt_n + cache_n` 应等于输入的 token 总数 → 对不上说明输入组织有问题。

### 3.3 资源指标

| 指标 | 采集方式 | 注意 |
| --- | --- | --- |
| 显存占用 | `nvidia-smi` | 须给出**服务启动前**的基线值，两者相减才是本服务占用 |
| KV 配置容量 | 启动参数 `-c` | 与"实测可用容量"分开记录 |

## 四、统计口径

| 项目 | 规则 |
| --- | --- |
| 样本单位 | **每个请求**是一条样本，不是每轮 |
| 分母 | 所有发出过的请求，**包括失败的** |
| 汇总方式 | 中位数与 P95 并列给出（平均值易被个别慢请求拉偏） |
| 轮次 | 每种核心配置至少 3 轮相同负载 |
| 冷启动 | 正式测量前先预热（跑几条丢弃的请求），避免首轮被初始化开销污染 |
| 缓存状态 | 每轮开始时记录缓存状态；跨轮次的前缀缓存命中要单独标注 |

**为什么失败要计入分母**：如果只统计成功的请求，失败率高的配置反而会"表现更好"——因为慢的、超时的都被排除了。这是自欺欺人。

## 五、并发场景的特殊说明

并发测试时，每个请求的 TTFT 会明显变差，原因是**排队**：

```
单并发：请求 A ──────────────▶ 完成

四并发：请求 A ──────────────▶ 完成
        请求 B   ────────────▶ 完成      ← 等 A 用完 slot 才开始
        请求 C     ──────────▶ 完成
        请求 D       ────────▶ 完成
```

因此并发测试要同时报告：

- **单个请求的 TTFT**（中位数、P95）——用户体感；
- **整批的总耗时**——系统吞吐。

**这两个指标往往朝相反方向走**：并发提高吞吐，但恶化单个请求的延迟。报告里必须把这对取舍讲清楚，不能只报好的那一个。

## 六、本阶段记录字段对照

`results/runs/*.jsonl` 中每条记录包含：

| 字段 | 对应指标 |
| --- | --- |
| `ttft_seconds` | TTFT |
| `client_seconds` | 总耗时 |
| `tpot_seconds` | TPOT |
| `completion_tokens` / `client_seconds` | 输出吞吐（可复算） |
| `prompt_tokens` / `completion_tokens` / `cached_tokens` | 服务端计数 |
| `server_timings` | 服务端各阶段耗时 |
| `status` / `error` | 成功与失败 |
| `concurrency` / `round` / `seq` | 并发配置与顺序 |
