# 配置级优化对比：结论

实验日期：2026-10-10
数据：`results/optimization/`、`results/runs/`
负载：v5，单并发 3 轮，同一台机器、插电、预热后

---

## 一、实验设计

**一次只改一项配置**，其余参数与负载完全一致。

| 配置 | 改动 | 预测 |
| --- | --- | --- |
| A 基线 | `-c 16384` | 基准 |
| B Flash Attention | 加 `-fa on` | 长上下文 prefill 更快、显存更省 |
| C KV 量化 | 加 `-ctk q8_0 -ctv q8_0` | KV 显存减半、容量翻倍，速度略降 |

**采用 A-B-A 设计**（基线 → 变体 → 基线重跑）：
多次运行之间显卡会升温，若按顺序只跑一次每个配置，
无法区分"配置的效果"和"设备状态漂移"。重跑一次基线用于检验可复现性。

## 二、结果

| 配置 | 运行编号 | 成功 | TTFT 中位 | 吞吐 | 墙钟 | 显存 |
| --- | --- | :-: | ---: | ---: | ---: | ---: |
| A 基线（第一次） | `20261010_110527` | 30/30 | 0.06 s | 76.7 t/s | 508.9 s | 7619 MiB |
| B Flash Attention | `20261010_111401` | 30/30 | 0.06 s | 73.3 t/s | 532.2 s | 8222 MiB |
| C KV q8 | `20261010_112300` | 30/30 | 0.06 s | 71.8 t/s | 545.4 s | 7022 MiB |
| **A2 基线（重跑）** | `20261010_113336` | 30/30 | 0.06 s | **76.7 t/s** | 508.7 s | — |

**相对基线：**

```
B Flash Attention：吞吐 −4.4%　TTFT +4.5%　墙钟 +4.6%　显存 +603 MiB
C KV q8：          吞吐 −6.4%　TTFT +14.3%　墙钟 +7.2%　显存 −597 MiB
A2 基线重跑：      吞吐 ±0%　  墙钟 −0.04%
```

## 三、漂移检查（这一步很关键）

三次运行按顺序跑完，吞吐恰好是 **76.7 → 73.3 → 71.8**，单调下降。
这种"随运行顺序整齐变慢"的形态很像设备热漂移，而**热漂移会把不同配置的差异伪装成配置效果**。

环境快照提供了证据：

| 运行 | 开始前温度 | 结束后温度 |
| --- | ---: | ---: |
| A（第一个跑） | **64 °C** | 86 °C |
| B | 79 °C | 86 °C |
| C | 80 °C | 86 °C |

第一次运行从冷态开始，后两次从 79~80 °C 开始。**温度差异确实存在。**

于是重跑一次基线（A2）。结果：

```
A  基线第一次：墙钟 508.9 秒　吞吐 76.7 t/s
A2 基线重跑：  墙钟 508.7 秒　吞吐 76.7 t/s
```

**两次基线几乎完全一致。** 说明在本实验的温度范围内，
热漂移并未造成可观测的吞吐差异——**B 与 C 的下降是配置本身的真实效果，
不是设备状态变化造成的。**

> 这一步的价值：先提出"可能是漂移"的竞争解释，再用实验排除它。
> 如果跳过这一步直接写结论，就无法排除读者对"顺序效应"的质疑。

## 四、KV 容量测量（本次优化的主要成果）

速度上 KV 量化是负优化，但**容量上的收益是明确的**。以 token 为单位测量：

| 配置 | KV 精度 | `-c` | 实际生效 | KV 显存 | 模型显存 |
| --- | :-: | ---: | ---: | ---: | ---: |
| 基线 | f16 | 8192 | 8192 | 1152 MiB | 2375.91 MiB |
| 基线 | f16 | 16384 | 16384 | 2304 MiB | 2375.91 MiB |
| KV q8 | q8_0 | 16384 | 16384 | **1224 MiB** | 2375.91 MiB |
| **KV q8** | q8_0 | **32768** | **32768** | **2448 MiB** | 2375.91 MiB |
| KV q8 | q8_0 | 65536 | **40960** | 4896 MiB | 2375.91 MiB |

### 三条结论

**1. KV 量化把 KV 显存降到约 53%**（2304 → 1224 MiB），略高于理论的一半，
差额来自量化块的额外开销。

**2. 同等显存下容量近似翻倍。**

```
基线：  KV 2304 MiB  →  16384 token
KV q8： KV 2448 MiB  →  32768 token     显存仅多 6%，容量翻倍
```

**3. 容量存在硬上限。** 请求 `-c 65536` 时实际只得到 **40960**——
这是模型自身的训练上下文长度，服务端加载时会自动截断并提示。
**继续加参数不会突破这个上限。**

### 这一条与基础阶段的边界问题直接相关

基础阶段曾在 `-c 8192`、四并发长文档时撞到容量边界：

```
E srv send_error: error: Context size has been exceeded.
```

当时四个 slot 合计占用 8916 token > 8192。改用 KV 量化后，
**在同样 8192 的**显存**预算下可以配置 16384 甚至更高的 `-c`，该边界随之消失。**

## 五、本次优化的判断

| 改动 | 速度 | 容量 | 显存 | 决定 |
| --- | --- | --- | --- | --- |
| Flash Attention | 慢 4.4% | 不变 | **多 603 MiB** | **不保留** |
| KV q8 | 慢 6.4% | **翻倍** | **少 597 MiB** | **保留**（当容量是瓶颈时） |

**理由：** 本项目的场景（8 人工作室、文档任务占多数）中，
长文档请求是常态，**容量不足会直接导致请求失败**（已实测），
而 6.4% 的吞吐下降在 0.06 秒的首字延迟上不可感知。
**在"失败"和"慢一点"之间，选择后者。**

### Flash Attention 为什么没带来收益

实测与预期相反。可能的原因（**未进一步验证，如实记录**）：

1. 本版本 llama.cpp 在该架构上对 `-fa` 的默认策略已是 `auto`，
   显式指定 `on` 未必走不同路径；
2. 本负载的输入最长约 2400 token，Flash Attention 的收益主要在更长上下文；
3. Blackwell 架构上该实现可能尚未充分优化。

**结论：在这台机器 + 这个版本 + 这个负载下，`-fa on` 是负优化。
不推广到其他配置，也不声称它是普遍结论。**

## 六、真正有效的吞吐优化：并发

三个配置级改动都没有提升吞吐。而此前测得的**并发**效果是明确的：

| 配置 | 吞吐 | 墙钟 | TTFT 中位 |
| --- | ---: | ---: | ---: |
| 并发 1 | 76.7 t/s | 508.9 s | 0.06 s |
| 并发 4 | **156.4 t/s** | **237.3 s** | **0.55 s** |

**吞吐提升 2.04 倍，代价是首字延迟恶化约 9 倍。**

这与 KV 量化的关系是：**并发越高，同时驻留的上下文越多，对 KV 容量的需求越大**。
因此三者的关系是：

```
提高并发  →  吞吐上升，但 KV 需求上升
              ↓
         需要更大容量
              ↓
    KV 量化在同等显存下把容量翻倍
```

**这是本项目唯一的完整优化链条**，也是最终采用的方案。

## 七、未解决与未验证

1. **未测 KV 量化对输出质量的影响。** 量化会改变数值，
   本轮 C 组出现 1 次输出截断（基线 0 次），提示输出可能受影响。
   **本项目未做质量对比，这是明确的缺口**；
2. **未测更高并发下的消化能力。** 并发 8、10 未测；
3. **未做组合实验。** `-fa on` 与 KV 量化同时开启的效果未测；
4. **Flash Attention 的负收益未定位到具体原因**，仅列出可能性。
