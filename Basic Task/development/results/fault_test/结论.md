# 故障与服务恢复：实验结论

实验日期：2026-10-10
实现：`src/supervisor.py`（服务管理）、`src/fault_test.py`（故障实验）
数据：`results/fault_test/`

---

## 一、实现了什么

### 1.1 服务管理器 `supervisor.py`

| 能力 | 做法 | 为什么这样做 |
| --- | --- | --- |
| 状态检测 | 通过 `/health` 判断，而非检查进程是否存在 | **进程活着不等于服务可用**：进程可能在但端口未监听、或已卡死 |
| 进程重启 | 先正常终止，超时后强制终止，再拉起新进程 | 避免旧进程残留占住端口 |
| 就绪确认 | 重启后持续轮询 `/health`，直到返回正常 | 进程启动到模型加载完成之间有十几秒空窗，只看进程存活就宣布"已恢复"是错的 |
| 事件记录 | 每次状态变化都带毫秒级时间戳写入时间线 | 报告需要"异常时刻、恢复时刻"这类可核查的时间证据 |

### 1.2 故障实验 `fault_test.py`

在负载运行途中**直接终止服务进程**（模拟真实崩溃，而不是先停服务再改配置），
监控线程自动检测并重启，同时记录每个受影响请求的最终状态。

## 二、三类请求的处理方式（本项目定义）

| 类别 | 定义 | 处理方式 | 计数口径 |
| --- | --- | --- | --- |
| **等待中** | 尚未发出的请求 | 等待服务恢复后再发，**不消耗重试次数** | 不计为失败 |
| **已发送** | 已发出但未收到完整响应 | 计入一次尝试，按上限重试 | 按 `request_id` 去重，只产生一条记录 |
| **失败** | 重试次数用尽，或等待超时仍未恢复 | 标记为 `failed`，记录原因 | **计入分母** |

**参数**：最大重试次数 3 次，每次重试间隔 5 秒，
单个请求等待服务恢复的**总预算 20 秒**（注意是每个请求一个总预算，
而不是每次尝试各等一份——后者会导致服务长期不可用时单个请求无限拖长）。

**去重**：同一 `request_id` 无论重试几次，只产生一条最终记录，
重试次数记录在 `attempts` 字段中，避免重试导致重复计数。

## 三、三个实验

| 实验 | 文档 | 故障时机 | 自动重启 | 覆盖类别 |
| :-: | --- | --- | :-: | --- |
| 1 | `20261010_104749` | 请求发出前 | 开 | 等待中 |
| 2 | `20261010_105010` | 请求执行途中 | 开 | 已发送 |
| 3 | `20261010_110039` | 请求执行途中 | 关 | 失败 |

### 实验 1：故障落在请求发出之前（等待中路径）

```
注入故障    直接终止服务进程
异常检出    健康检查失败：Connection refused
请求等待    P04 服务不可用，等待恢复后再发
恢复完成    重启并就绪，用时 2.5 秒
等待结束    P04 累计等待 3 秒，服务已恢复
       → ok（尝试 1 次）
```

**结果：10/10 成功，重试 0 次。** 请求在发出前就等服务恢复，没有产生失败。

### 实验 2：故障落在请求执行途中（已发送路径）

```
计划注入    3 秒后终止服务
注入故障    直接终止服务进程
请求失败    P04 第 1 次尝试：RemoteDisconnected: Remote end closed connection without response
恢复完成    重启并就绪，用时 3.0 秒
       → ok（尝试 2 次）
```

**结果：10/10 成功，其中 1 条经重试恢复；总尝试 11 次，记录 10 条（无重复计数）。**

这一条最关键：请求**已经发出去**了，服务被杀导致连接中途断开，
客户端收到 `RemoteDisconnected`。重试一次后成功——说明"已发送"类的重试策略有效。

### 实验 3：关闭自动重启（失败路径）

```
请求失败    P04 第 1 次尝试：RemoteDisconnected ...
等待结束    P04 累计等待 20 秒，服务仍不可用
请求放弃    P04 服务不可用，等待 20 秒后仍未恢复，剩余请求不再发出
       → failed
...
手动恢复    负载结束，执行一次恢复（3.0 秒就绪）
恢复验证    成功：收到回答 109 字符，用时 0.58 秒
```

**结果：3/10 成功，7 条失败（P04 已发送后断开，其余 6 条等待超时未发出）。**

这一步验证了两件事：

1. **重试上限与等待预算确实生效**，服务长期不可用时请求会以 `failed` 结束，
   而不是无限重试；
2. **失败请求被计入分母**（成功 3 / 总数 10），没有因为失败而被排除在统计之外。

## 四、关键数字

| 指标 | 数值 | 说明 |
| --- | ---: | --- |
| 异常检出到恢复完成 | **2.5 ~ 3.0 秒** | 监控每秒检测一次 |
| 进程重启到就绪 | **1.5 ~ 4.3 秒** | 模型文件在页缓存中，加载较快 |
| 已发送请求的重试恢复 | **1 次重试即成功** | 服务恢复即自动续上 |
| 记录去重 | 11 次尝试 → 10 条记录 | 重试不产生重复计数 |

## 五、还没做到的边界

1. **恢复耗时是在理想条件下测得的。** 本机模型仅 2.4GB 且在页缓存中，
   重启只需 1.5~4.3 秒。若模型更大、或需要从磁盘冷加载，恢复窗口会显著变长，
   20 秒的等待预算可能不够。**该预算应按实际模型加载时间重新标定**；
2. **只验证了单进程崩溃。** 端口被占用、进程僵死但端口仍监听等场景未覆盖；
3. **重试未加退避。** 当前每次间隔固定 5 秒。服务刚恢复时若同时涌入多个重试请求，
   可能造成瞬时压力，后续可改为指数退避；
4. **未验证恢复期间的数据一致性。** 中途断开的请求是否在服务端留下半截状态，
   本次未检查。
