# 进阶题结论：缓存感知的请求调度

实验日期：2026-10-10
实现：`src/scheduler.py`（调度模块）、`src/replay.py`（回放驱动）
数据：`results/advanced/`

---

## 一、问题与方案

### 1.1 问题

参考请求序列含 16 条请求，到达时间 0~6000 ms：

- **8 条交互式**：期限 15~45 秒，用户在现场等待；
- **8 条后台**：期限 180~240 秒，可以等待。

若按到达先后处理，交互式请求会排在后台请求之后。实测 FIFO 下
**8 条交互式请求全部超期**——这是业务上不可接受的。

### 1.2 三种策略

| 策略 | 规则 |
| --- | --- |
| FIFO | 先到先服务（基线） |
| priority | 交互式优先；同类内期限早的优先 |
| priority_cache | 在 priority 基础上，优先选择能与"最近处理过的会话"共享前缀的请求 |

**优先级用规则查表产生，不调用模型**，因此决策开销可忽略。
若改用决策模型，其调用耗时必须计入端到端指标。

## 二、实验设计中的一个关键修正

第一版实验把三种策略的 9 轮全部跑在**同一个服务会话**上。
结果发现：**"首次出现"的会话也命中了 99% 的缓存**——

```
R01  docs-v1-a  该会话的第一条请求   prompt 766  命中 765
R05  docs-v1-b  该会话的第一条请求   prompt 775  命中 774
```

这说明**上一轮留下的前缀仍在 KV 池中**。残留缓存压倒了策略差异，
导致三种策略的 `cached_tokens` 几乎相同，**测不出调度的影响**。

**修正：每轮开始前重启服务清空缓存**，三种策略从相同的冷状态出发。
重启耗时约 2 秒，对实验总时长影响可忽略。

> 题包的参考测试文档也提示过这一点："缓存实验记录跨运行保留和清理的状态"。

## 三、结果（冷缓存，每策略 3 轮）

| 策略 | 轮次 | 按期率 | 交互等待中位 | 后台等待中位 | 后台最大等待 | 缓存命中 |
| --- | :-: | ---: | ---: | ---: | ---: | ---: |
| FIFO | 1 | 56% | 39.3 s | 40.1 s | 71.9 s | 3619 |
| | 2 | 56% | 36.4 s | 37.6 s | 69.6 s | 3619 |
| | 3 | 56% | 36.9 s | 38.0 s | 69.5 s | 3619 |
| **priority** | 1 | **100%** | 7.2 s | 52.5 s | 72.5 s | 4952 |
| | 2 | **100%** | 13.5 s | 72.3 s | 94.0 s | 4952 |
| | 3 | **100%** | 6.5 s | 51.4 s | 71.1 s | 4952 |
| **priority_cache** | 1 | **100%** | 6.6 s | 55.7 s | 70.7 s | 4893 |
| | 2 | **100%** | 6.6 s | 55.0 s | 71.5 s | 4893 |
| | 3 | **100%** | 6.9 s | 56.8 s | 75.4 s | 4893 |

**均值对比：**

| 策略 | 按期率 | 交互等待 | 后台等待 | 后台最大等待 | 缓存命中 |
| --- | ---: | ---: | ---: | ---: | ---: |
| FIFO | 56% | 37.5 s | 38.6 s | 70.3 s | 3619 |
| priority | **100%** | **9.0 s** | 58.7 s | 79.2 s | **4952** |
| priority_cache | **100%** | **6.7 s** | 55.8 s | 72.5 s | 4893 |

三轮之间结果高度一致（缓存命中数完全相同），说明测量可复现。

## 四、结论

### 4.1 优先级调度是决定性的

```
按期率：      56%  →  100%
交互等待中位：37.5 s  →  9.0 s     快 4.2 倍
```

**这是本次实验最大的收益，也验证了预测。**

### 4.2 代价明确且可接受

```
后台等待中位：38.6 s  →  58.7 s    变长 52%
后台最大等待：70.3 s  →  79.2 s    变长 13%
```

后台请求的期限是 180~240 秒，等 59 秒仍在期限内，
**其按期率并未下降**。**用户看不见的等待变长，用户看得见的等待变短**——这是划算的交换。

### 4.3 缓存亲和规则没有带来额外收益（与预测不符）

预测是"缓存感知会提高 cached_tokens"，实测**没有**：
`priority_cache` 的缓存命中 4893，反而比 `priority` 的 4952 低 1.2%。

**原因（已定位）**：`R08` 是交互式请求，`priority` 规则本来就把它排在很前面，
紧跟同会话的 `R01` 之后。**缓存亲和没有可优化的空间。**

### 4.4 一个未预期的发现：优先级调度本身提高了缓存命中

```
缓存命中：FIFO 3619  →  priority 4952     提高 37%
```

**机制**（逐请求数据支持）：

| 策略 | R01（会话首条） | R08（同会话第二条） | R15（第三条） |
| --- | ---: | ---: | ---: |
| FIFO | 0 | **0** | 765 |
| priority | 0 | **774** | 765 |
| priority_cache | 0 | 715 | 765 |

FIFO 下 `R01` 与 `R08` 之间隔了 6 条请求，而服务只有 **4 个 slot**，
`R01` 的前缀已被挤出，`R08` 只能重算（命中 0）。
priority 下 `R08` 紧跟 `R01`，前缀仍在，几乎全部命中（774）。

**这揭示了一条比"排序优化"更本质的规律：**

> 前缀复用能否命中，取决于**同一前缀的后续请求是否在前缀被挤出之前得到处理**。
> 而"挤出"由 slot 数量与中间插入的请求数共同决定。
> **调度顺序直接决定缓存的可得性。**

这也解释了为什么单纯加"缓存亲和"规则收效甚微——
**当优先级规则已经把相关请求聚拢时，缓存收益是自动获得的副产品，不需要额外机制。**

## 五、代价与边界

### 5.1 代理/调度层的开销

调度决策为纯规则查表，开销可忽略（未单独计时）。
但**单工作线程串行处理**是本实验的设定，实际部署需要并发工作线程，
届时等待时间与缓存行为都会改变——**本次结论不直接适用于并发调度**。

### 5.2 公平性

| 指标 | FIFO | priority | 变化 |
| --- | ---: | ---: | ---: |
| 后台最大等待 | 70.3 s | 79.2 s | +13% |
| 后台按期率 | 100% | 100% | 不变 |

**未出现低优先级请求被饿死。** 原因是后台请求期限宽松（180~240 秒），
而交互式请求在 45 秒内全部处理完，之后队列只剩后台请求，可以连续处理。

### 5.3 未验证

1. **并发调度未测。** 本实验串行处理以隔离"调度顺序"这一个变量；
2. **更多会话复用场景未测。** 序列中只有 2 个会话含多条请求
   （`docs-v1-a` 3 条、`code-a` 2 条），缓存亲和的用武之地有限；
3. **未测试 slot 数量变化的影响。** 4.4 节的机制推断指出 slot 数决定缓存能否保留，
   但未做"slot 数 × 调度策略"的交叉实验；
4. **未使用决策模型判断优先级**，因此无法报告"决策开销"这一项。

## 六、最终判断

| 机制 | 收益 | 代价 | 决定 |
| --- | --- | --- | --- |
| priority 调度 | 按期率 56%→100%，交互等待 −76% | 后台等待 +52%（仍在期限内） | **保留** |
| priority_cache | 无额外收益（−1.2%） | 无 | **不保留** |

**最终方案：采用优先级调度，不叠加缓存亲和规则。**

理由：收益确定、代价可控、机制可解释；而缓存亲和在实际负载下
已被优先级规则覆盖，增加复杂度却无收益——**保留一个没有收益的机制，
只会让系统更难维护和解释**。
