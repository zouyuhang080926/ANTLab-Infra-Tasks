# 边界发现：并发长文档会撑爆 KV 池

发现日期：2026-10-09

## 一、现象

在 `-c 8192`（统一 KV 池 8192 token）、并发 4 的情况下，服务端出现错误：

```
E srv    send_error: task id = 711, error: Context size has been exceeded.
E srv    send_error: task id = 992, error: Context size has been exceeded.
E srv update_slots: decode() failed: Context size has been exceeded.
```

客户端表现（`results/runs/20261009_212420.jsonl`）：

| 任务 | 现象 |
| --- | --- |
| D03 | 返回**空回答**，0 字符，用时 0.375 秒 |
| D02 | 只返回 14 个字符 |
| D01 / P03 / C01 / C02 / D04 | 有内容但 `finish_reason` 与 `usage` 缺失，**流在结尾处被掐断** |

## 二、原因

服务启动时日志显示 4 个 slot 共享一个统一 KV 池：

```
load_model: initializing, n_slots = 4, n_ctx_slot = 8192, kv_unified = 'true'
```

出错瞬间各 slot 持有的 token 数：

| slot | 持有 token |
| ---: | ---: |
| 0 | 1146 |
| 1 | 2646 |
| 2 | 1931 |
| 3 | 3193 |
| **合计** | **8916** |

**8916 > 8192**：四个请求的输入加已生成内容之和超过了池子容量，服务端无法继续分配，
于是取消任务并返回错误。

关键点：**KV 池同时容纳"输入"和"已生成的内容"。** 所以判断容量是否够用，
不能只看输入长度，要按 `输入 token + 预期输出 token` 估算每个请求的需求。

## 三、容量估算

逐个请求按"输入 + 输出上限"估算最坏需求：

| 任务 | 输入 | 输出上限 | 最坏需求 |
| --- | ---: | ---: | ---: |
| C02 | 1936 | 4096 | 6032 |
| D01 | 2371 | 2048 | 4419 |
| D02 | 2367 | 1536 | 3903 |
| C01 | 1727 | 2048 | 3775 |
| D03 | 1931 | 1536 | 3467 |
| D04 | 1918 | 1536 | 3454 |

按本负载的执行顺序，并发 4 时同时运行的组是
`{P01,P02,P03,P04}` → `{D01,D02,D03,D04}` → `{C01,C02}`。
其中第二组的最坏需求合计约 **15243 token**，已接近 8192 的两倍。

## 四、处理

把 KV 池从 **8192 提到 16384** 后重跑，四并发 30/30 全部正常结束，
服务端不再出现 `Context size has been exceeded`。

| 配置 | KV 池 | 显存占用 | 四并发结果 |
| --- | ---: | ---: | --- |
| 原配置 | 8192 | 约 5.7 GB | 失败：容量超限 |
| 调整后 | 16384 | 约 7.9 GB | 成功：30/30 |

## 五、这个发现说明了什么

1. **并发能力不是无限的**，它由 KV 池容量决定，而不是由 slot 数量决定；
2. **"并发数"不能单独评估**，必须与"每个请求的上下文规模"一起考虑；
3. 提高容量需要付出显存代价（8192→16384 时显存增加约 2.2 GB），
   这是典型的"容量与资源"取舍；
4. 失败时**不能只统计成功请求**——若把空回答和截断响应当作成功，
   结论会完全失真。

## 六、客户端程序暴露出的问题（已修复）

首轮并发测试时，客户端把"流被中途掐断"的响应记成了 `status = ok`。
这是危险的做法：**残缺数据不声不响地混进了结果**。

修复方式：流式响应正常结束时必然带一个 `usage` 分片；
收不到 `usage` 就标记为 `incomplete`，并保留已收到的部分内容与错误原因。
